# Go 代码性能优化

## 作用范围

这个 Skill 用于帮助在当前仓库中优化 Go 代码，重点关注：

- 性能（CPU 和内存）
- 内存分配减少与逃逸分析
- 并发模式（`goroutine`、`channel`、`sync` 原语）
- Go 惯用写法与代码简化

默认假设 Agent 已经了解通用的 Go 最佳实践，这里只补充与本项目和典型工作流相关的指导。

## 快速工作流

当用户希望优化或加速 Go 代码时：

1. **明确优化目标**
   - 找出性能敏感的包、文件或函数（例如：消息处理、WebSocket 循环、protobuf 编解码、游戏状态更新等）。
   - 如果用户没有明确说明，就在 `core/`、`service.go` 等文件中，优先查找：紧密循环、频繁创建 goroutine 的位置、序列化相关代码等潜在热点。

2. **建立基线（Baseline）**
   - 建议在项目根目录执行：
     - 一般性检查：`go test ./...`，确保在优化前先通过测试。
     - 若已有基准测试：`go test -bench . ./...`。
   - 如不存在基准测试，并且用户同意，可建议围绕热点函数补充针对性的 micro benchmark。

3. **先做 Profiling 再猜测**
   - CPU 分析（CPU profile）：
     - 在合适的测试或小型运行脚本中，新增或复用 `-cpuprofile` 参数。
     - 示例命令（存在 benchmark 时）：`go test -bench . -benchmem -cpuprofile cpu.out ./...`。
   - 内存与分配：
     - 使用 `-benchmem`，关注 `ns/op`、`B/op` 和 `allocs/op`。
   - 使用 `go tool pprof` 分析生成的 profile 文件，定位最热函数、高分配点和代价昂贵的调用栈。

4. **分析热点路径（Hot Path）**
   - 优先关注以下特征的函数：
     - 累计 CPU 时间占比高。
     - `B/op` 或 `allocs/op` 明显偏大。
   - 排查点包括：
     - 不必要的分配（如：循环中多次 `append` 却没有预估容量、在循环中频繁创建临时切片或 map）。
     - 过多的字符串拼接（考虑使用 `strings.Builder`）。
     - 在紧密循环中大量使用接口或反射。
     - 热路径上的同步 I/O 操作。

5. **给出具体的优化方案**
   - 对每个热点，给出明确可执行的修改建议，例如：
     - 如果能预估大小，就提前为切片或 map 预分配容量。
     - 在合适场景下复用缓冲区，或引入 `sync.Pool`。
     - 避免在 goroutine 闭包中捕获大对象，改为传指针或小结构体。
     - 对热路径中使用 `interface{}` 或反射的地方，改用具体类型。
     - 简化控制流，减少不必要的分支，同时提高可读性。

6. **确保并发正确性**
   - 在优化 goroutine 和 channel 使用时：
     - 不要删除必要的同步逻辑。
     - 对引入共享状态或缓冲区复用的修改，注意潜在数据竞争。
     - 在做出较大的并发相关改动后，建议运行 `go test -race ./...`。

7. **修改后的验证**
   - 必须做到：
     - 再次执行 `go test ./...`，确保没有引入回归问题。
     - 重新运行相关基准测试（或新增基准测试），对比前后指标。
   - 以量化方式汇报提升效果，例如：
     - “ns/op 从 X 降低到 Y”
     - “allocs/op 从 A 降低到 B”

## 与本项目相关的优化提示

本项目是使用 Go + WebSocket + protobuf + goroutine 实现的实时画布 / 聊天应用，注意：

- 需要重点关注：
  - 消息的编码 / 解码（protobuf 使用）。
  - WebSocket 读写循环。
  - 游戏状态更新循环和广播逻辑。
- 此类应用的常见优化点：
  - 在向大量客户端广播时，避免每条消息都重新分配对象。
  - 在安全的前提下，复用 protobuf 消息结构体或缓冲区。
  - 避免在主事件循环中执行阻塞操作。

## 如何向用户汇报优化结果

在对用户说明优化工作时：

1. **总结瓶颈**
   - 简要说明哪些函数或代码路径存在性能或分配问题。

2. **解释修改内容**
   - 用高层次语言概述每一项优化（无需整文件贴代码，除非用户特别要求）。
   - 同时说明性能上的原因和 Go 惯用写法上的考量。

3. **展示前后对比指标**
   - 给出来自 `go test -bench` 或 profiling 的关键数据（CPU 时间、`ns/op`、`B/op`、`allocs/op` 等）。

4. **指出潜在风险**
   - 标记所有涉及并发模型变更的部分，提醒需要额外审查。
   - 建议在涉及并发的改动后执行 `go test -race ./...` 以增加安全性。
