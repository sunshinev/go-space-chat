# Go 代码 Review（CR）

## 作用范围

这个 Skill 用于在当前仓库里做 Go 代码 Review，重点关注：

- WebSocket 处理及消息流转
- 基于 Protobuf 的序列化 / 反序列化
- Goroutine 与 channel 的使用
- HTTP 处理函数与相关 API
- `core/` 及相关包中的项目特定模式

默认假设 Agent 已经了解 Go 的通用最佳实践，这里重点是如何在本项目中一致、正确地应用这些实践。

## Review 工作流

当用户请求对 Go 代码进行 Review（CR）时：

1. **明确 Review 对象**
   - 确认本次 Review 的范围是：
     - 某个具体文件（例如：`core/service.go`）
     - 一组改动（git diff、Pull Request 或补丁）
     - 某个新功能或 bug 修复的完整流程
   - 如果有 diff（`git diff`、PR 变更）可用，优先从 diff 入手，再按需扩展到周边上下文。

2. **建立上下文认知**
   - 快速浏览相关类型和函数：
     - 对处理函数（handler），查看它是在哪里注册的、怎样被调用。
     - 对 Protobuf 消息类型，必要时查阅 `proto/` 目录下的定义（如存在）。
   - 理解这段代码的主要职责，例如：WebSocket 升级、消息解析、消息广播、登录统计等。

3. **正确性与错误处理**
   - 检查是否：
     - 所有错误要么被妥善处理，要么被有意忽略并附有合理说明。
     - `defer` 的使用位置正确，避免出现在高频内层循环中。
     - `json.Marshal/Unmarshal` 与 `proto.Marshal/Unmarshal` 的错误都被检查。
     - HTTP 处理函数设置了合理的状态码和响应头。
   - 留意：
     - 潜在的 nil 指针解引用。
     - 值接收者 vs 指针接收者是否被误用。
     - 类型断言 `.(*T)` 是否缺乏检查或可能 panic。

4. **并发与安全性**
   - 检查 goroutine 与同步逻辑：
     - 访问共享状态（`map`、`slice`、共享结构体等）时是否存在明显的数据竞争风险。
     - `sync.Mutex` / `sync.RWMutex` 与 `sync.Map` 的使用是否一致且合理。
     - WebSocket 连接的并发读写是否遵循 gorilla/websocket 的推荐做法（通常为：每个连接一个读 goroutine、一个写 goroutine，或通过加锁串行化写入）。
   - 针对 channel：
     - 校验发送 / 接收模式是否可能导致死锁。
     - 避免与 channel 相关的 goroutine 无上限创建且缺乏清晰生命周期管理。

5. **性能与资源管理**
   - 检查是否存在：
     - 热路径中的不必要分配（循环、消息处理、广播等）。
     - 可以缓存却被重复执行的工作（例如重复解析、相似消息重复分配缓冲区）。
     - 资源是否被正确关闭：WebSocket 连接、HTTP Body（作为客户端时）、文件句柄等。
   - 确保：
     - 在极其频繁的内层循环中尽量避免使用 `defer`。
     - 日志输出在紧密循环中不过度，以免拖累性能。

6. **API 行为与对外契约**
   - 确认：
     - 对外可见的类型和函数（导出符号）行为清晰稳定。
     - HTTP 处理函数（`http.HandlerFunc`）返回的 JSON 结构与 `Content-Type` 等保持一致且可预期。
     - 行为上的不兼容变更是有意为之，并在 Review 评论中点明。

7. **Go 惯用法与可读性**
   - 鼓励：
     - 函数职责单一、体积适中。
     - 惯用的命名方式（短接收者名、`ctx` 作为 context 变量名等）。
     - 使用提前返回（early return）减少嵌套层级。
   - 指出：
     - 过于复杂的条件判断或深层嵌套的代码块。
     - 错误信息或日志格式不一致的问题。

8. **安全性考量**
   - 对所有面向外部的 Web / WebSocket 代码：
     - 检查用户输入是否被适当校验和清洗（HTML 转义、防止 XSS 等）。
     - 核对跨域策略或 WebSocket 升级（`CheckOrigin`）是否是有意的配置。
     - 确保不会在日志中泄露敏感信息（如 Token、隐私数据等）。

9. **测试情况**
   - 若被 Review 的代码已有测试：
     - 检查是否覆盖了主流程（happy path）和关键边界场景。
     - 在涉及并发或复杂错误处理时，建议补充有针对性的测试。
   - 若缺少测试：
     - 推荐添加集中、关键路径的单元测试或简单集成测试，而不是要求面面俱到。

## Review 反馈的组织方式

当回应一次 Go CR 请求时：

1. **高层总结**
   - 用 1–3 句概括这段代码在做什么、整体质量如何（优秀 / 可以 / 存在风险）。

2. **按类别归纳问题**
   - 将评论归类到如下小节中，例如：
     - **Correctness（正确性）**
     - **Concurrency（并发）**
     - **Performance（性能）**
     - **Readability / Style（可读性 / 风格）**
     - **Security（安全性）**
   - 对每条问题：
     - 简要说明问题所在。
     - 给出具体的修改建议或可选方案。

3. **标注优先级**
   - 大致将问题标记为：
     - **Must fix**：影响正确性、可能导致数据竞争 / panic / 明显 bug。
     - **Should fix**：对可维护性或性能影响较大的问题。
     - **Nice to have**：主要是风格或小的可读性优化。

4. **代码引用方式**
   - 在可能的情况下，优先通过函数名和行区间来引用代码，而不是整文件贴出。
   - 只有在能够明显帮助理解改动建议时，才贴出小段代码。

## 适合触发本 Skill 的示例问题

- "帮我 review 一下 `core/service.go` 这个文件的 Go 代码质量。"
- "下面这段 Go diff 有什么问题？从并发安全和可读性上帮我看下。"
- "这次提交主要修改了 WebSocket 广播逻辑，帮我做一次详细的 Go 代码 CR。"
